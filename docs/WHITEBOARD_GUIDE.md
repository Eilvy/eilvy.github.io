> 面向「用 Excalidraw 画板给文章配图」的实操文档。
> 记录布局技巧与踩过的坑，避免重复摸索。
>

## 0. 快速开始

```ts
// 1. 写场景数据：src/components/whiteboard/xxx.scenes.ts
import { C, box, txt, hFlow, arrowTo, type El } from './scene-kit';

export const myScene: El[] = [
	txt(40, 30, '标题', 22),
	txt(42, 68, '副标题，一句话说清这张图在讲什么', 13, C.muted),
	box(40, 120, 200, 76, '节点文字', C.node, 15),
];
```

```mdx
<!-- 2. 在文章里引用（文章需为 .mdx） -->
import WhiteboardLoader from '../../components/whiteboard/WhiteboardLoader.astro';
import { myScene } from '../../components/whiteboard/xxx.scenes';

<WhiteboardLoader
	elements={myScene}
	label="给读屏软件的完整描述"
	buttonText="点击加载流程图"
	height={560}
/>
```

**只画一套浅色配色**，暗色交给 Excalidraw 反相（见第 2 节）。

## 1. 可用件（scene-kit.ts）

| 件 | 签名 | 用途 |
|---|---|---|
| `txt` | `(x, y, text, size?, color?)` | 纯文本（标题、副标题、说明） |
| `box` | `(x, y, w, h, label, fill, size?)` | 圆角节点框，文字**自动居中** |
| `vArrow` | `(x, y1, y2, color?, label?)` | 竖直箭头 |
| `hFlow` | `(x1, x2, y, color?, label?)` | 水平单向箭头（串流程用） |
| `hArrow` | `(x1, x2, y, color?, label?)` | 水平**双向**箭头 |
| `arrowTo` | `(x1, y1, x2, y2, color?, label?)` | **任意方向**（含斜向） |
| `groupFrame` | `(x, y, w, h)` | 虚线范围框 |
| `vStack` | `(steps, opts)` | 竖直流程布局（自动排节点 + 箭头） |

坐标系：**y 轴向下**，`box(x, y, w, h)` 的 `(x, y)` 是左上角。

## 2. 配色

### 只画一套浅色配色

**不要为暗色另准备一套颜色。** Excalidraw 在暗色下会给整块画布套：

```css
filter: invert(93%) hue-rotate(180deg)
```

深色字会自动变成亮色、白底变深底。

> **踩过的坑**：一开始我为暗色单独准备了「浅色文字」，结果被**再反相一次**变回深色，
> 出现「暗底 + 暗字」几乎看不见。等于跟框架对着干，还多反了一次。

### 两套语义色板

`C` 里有两组名字，**取值相同**，只是语义不同：

| 组 | 键 | 适用 |
|---|---|---|
| OSI 分层 | `l1`…`l5` | 网络分层类文章（物理层/链路层/…） |
| 通用语义 | `external` / `node` / `rule` / `pod` / `lb` | 其他场景（如 k8s Service 拓扑） |

另外 `C.text`（正文）、`C.muted`（次要说明）、`C.emphasis`（强调/红）、
`C.neutral`（中性底）、`C.warn`（警示底）。

**为什么分两组**：在 Service 的图里写 `C.l3` 没人看得懂，写 `C.node` 一目了然。
两组取值一致，所以全站观感统一。

### 同色系要一致

同一篇文章里，同一类对象用同一个颜色。例如 OSI 那篇：
L1 橙、L2 黄、L3 蓝、L4 绿、L5-7 紫 —— 6 张图全部一致，
读者扫一眼颜色就知道当前在哪一层。

## 3. 字体：必须用本地字体

场景里的文字**一律用 `FONT_LOCAL`（Helvetica，`fontFamily: 2`）**。
`box` / `txt` 已内置，不用手动传。

> **踩过的坑**：Excalidraw 默认的 Excalifont 与中文回退 Xiaolai 是
> **运行时从 unpkg CDN 按需拉取**的，中文子集约 200+ 个、总计约 12MB。
> 加载失败时文字按 fallback 字体渲染，而元素宽度是按另一字体量出来的 ——
> 结果是文字**超出文本框被裁切**（实测副标题末尾字符被切掉）。
>
> Helvetica 在 Excalidraw 里标记为 `local`，直接用系统字体，取宽与渲染一致。

## 4. 箭头

### 4.1 标注一律用箭头的 `label`

```ts
hFlow(480, 600, 215, C.emphasis, 'veth pair')   // ✅ 自动居中
```

**不要**另写一个 `txt` 摆在箭头旁边。

> **踩过的坑**：早期用独立 `text` 手工摆坐标，实测偏差：
> - 「虚拟数据通道」相对箭头中点 `dx=-18 / dy=+71`
> - 「host 端插在网桥上」相对箭头中点 `dx=+191`
>
> 根因：箭头位置是**算出来**的（如 `hostVeth.x + hostVeth.w`），
> 而标注坐标是**硬编码**的，两者不可能自动对齐；
> 箭头一改，标注还会继续错位。

### 4.2 label 过大会盖住箭头

label 太长时会在箭头上**折成多行、把箭头压住**。实测把
「xmit() 直接调用对端 rx()：函数调用，不是网络传输」塞进 100px 宽的箭头，
折成三行并覆盖箭头。

两个对策（通常要同时做）：

1. **放宽箭头间距**（100px → 220px）
2. **标注只留核心短语**，细节移到下方正文

### 4.3 选对箭头函数：汇合必须用斜线

| 场景 | 用哪个 |
|---|---|
| 正上正下 | `vArrow` |
| 正左正右、串流程 | `hFlow` |
| 双向水平 | `hArrow` |
| **两条链汇入同一节点** | **`arrowTo`**（斜线） |

> **踩过的坑**：NodePort 图里两条链要「汇合到 DNAT」，我用 `hFlow` 画水平线，
> 结果两个箭头**都指向方框外的空白**。原因：两条链出口在 y=158 / y=338，
> 而目标方框纵向只有 210–286 —— 水平线终点自然落在方框上下，汇合关系根本没画出来。

### 4.4 箭头终点必须落在目标框内

画完**务必自查**每个箭头的终点是否真的指到某个方框（而不是悬在空白里）。
这是最容易犯又最不容易被发现的错误。

一个粗糙但有效的检查思路：把每个箭头的终点坐标与所有 `box` 的矩形比对，
看是否落在某个矩形边界内（允许几像素误差）。

## 5. 布局

### 5.1 画布尺寸与内容比例

内嵌画布实际约 **686px 宽**，高度由调用方传的 `height` 决定。
Excalidraw 的 `fitToViewport` 按「**完整装下内容**」来缩放，
所以**内容越宽，缩得越小、文字越小**。

> **实测**：内容宽约 900px 时被压到 **80%**；收紧到约 760px 后接近 **90%**，
> 同屏文字明显更清楚。

**结论**：横向跨度尽量控制在 **760px 以内**，别为了「铺开」把图拉宽。

### 5.2 高窄内容会被压小

若内容又窄又高（例如 640×900），会被压得很小、文字难读。

**对策：把说明文字并入节点内部**（多行 label），而不是单独摆在旁边。

```ts
// ✅ 内容接近画布比例
box(40, 120, 560, 76, 'L2 数据链路层\nMAC 校验、剥离以太网帧头、触发硬中断', C.l2)

// ❌ 节点窄 + 右侧长说明 → 整体又宽又扁或又窄又高
box(40, 120, 200, 76, 'L2 数据链路层', C.l2)
txt(260, 140, 'MAC 校验、剥离以太网帧头、触发硬中断', 13)
```

### 5.3 文字与图形不要重叠

用 `box` 时文字自动居中，无需操心；但**独立的 `txt` 要自己避开图形和箭头**。

> **踩过的坑**：
> - iptables 图的长说明压到了右侧方框上
> - clusterIp 图的说明文字正好被竖直箭头**穿过**

对策：说明文字与图形之间留出间隔，或移到箭头不经过的一侧。

### 5.4 范围框的名字放在框外

`groupFrame` 本身不带 label —— Excalidraw 的 `label` 会**居中压在框内节点上**。
范围名（如「宿主机侧」「Pod 侧」）应单独用 `txt` 放在框**上方外侧**。

### 5.5 范围框要先入数组

`groupFrame` 要排在内部节点**之前**，否则会盖住节点（Excalidraw 按数组顺序绘制）。

### 5.6 竖直流程用 `vStack`

节点多、间距一致时用 `vStack`，只描述「有哪些步骤」：

```ts
...vStack(
	[
		{ label: '物理网卡 eth0\nL1：电信号 → 比特流', fill: C.l1 },
		{ label: 'L2 数据链路层\nMAC 校验、剥离帧头', fill: C.l2 },
	],
	{ x: 40, y0: 120, w: 560, h: 76, gap: 52 }
)
```

比手写坐标少犯错，也便于统一调间距。

## 6. 内容组织

### 6.1 先给总览，再逐层拆解

多张图讲一条链路时，开头先来一张**横向总览**（把整条路径铺开），
后面再逐跳细讲。否则读者「见树不见林」。

### 6.2 保留 ASCII 折叠版

把原图/文字流程收进 `<details>`，兼顾：

- 读者复制文本
- 无 JS 环境
- 搜索引擎与读屏软件

```mdx
<details>
<summary>等价的 ASCII 图（便于复制 / 无 JS 环境）</summary>

```
（原 ASCII 图）
```

</details>
```

### 6.3 颜色承载语义

同一层/同一类用同色，让读者不读文字也能定位。例如 Service 那篇：
`external`（外部）橙、`node`（宿主机）蓝、`rule`（规则）黄、`pod`（后端）绿。

## 7. 交付前自查清单

- [ ] **箭头终点**是否都落在目标方框内（不是空白）
- [ ] 汇合/斜向连线是否用了 `arrowTo`（而非 `hFlow`）
- [ ] 箭头标注是否用 `label`（而非独立 `txt`）
- [ ] label 是否过长导致折行盖住箭头
- [ ] 独立 `txt` 是否与图形/箭头重叠
- [ ] 内容横向跨度是否 ≲ 760px
- [ ] 同一篇文章内配色是否一致
- [ ] 是否只画了一套浅色配色（没为暗色另写）
- [ ] 是否保留 ASCII 折叠版
- [ ] **浅色与暗色都实际看一眼**

## 8. 验证方式

```bash
npm run dev     # 改画板后必须看 dev（HMR 与生产行为不同）
npm run build   # 再看构建产物
npm run check   # 类型检查
```

**截图核对的注意点**：headless Chrome 的 `--virtual-time-budget`
**不会等动态 import 的网络请求**，自动点击后截图常停在加载态。
此时改用 DOM 实测更可靠：读取 `canvas` 是否存在、`getBoundingClientRect()` 的
尺寸与位置，以及「元素是否真的可见」。

## 附：踩坑速查

| 现象 | 根因 | 对策 |
|---|---|---|
| 暗色下文字过暗 | 为暗色多准备了一套配色，被反相两次 | 只画一套浅色配色 |
| 文字被裁切 | CDN 字体加载失败，取宽与渲染不一致 | 用 `FONT_LOCAL` |
| 箭头标注偏离 | 标注是独立 `txt`、坐标硬编码 | 改用箭头 `label` |
| label 盖住箭头 | 文字过长在箭头上折行 | 放宽箭头间距 + 缩短文字 |
| 箭头指向空白 | 用 `hFlow` 画「汇合」，终点落在方框外 | 汇合用 `arrowTo` 斜线 |
| 文字与图形重叠 | 独立 `txt` 没避开图形/箭头 | 留间隔或换位置 |
| 图整体偏小、字难读 | 内容横向跨度过大，被 `fitToViewport` 压小 | 跨度控制在 ≲760px |
| 范围框名字压住节点 | `groupFrame` 的 label 居中在框内 | 名字用 `txt` 放框外上方 |
| 范围框盖住节点 | 数组顺序在节点之后 | `groupFrame` 先入数组 |
| 内嵌画板能被拖动 / 滚轮被抢 | Excalidraw 的 canvas 行为 | 已由组件处理，改画板时无需管 |
