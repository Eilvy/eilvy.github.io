「HTTP/2 比 HTTP/1.1 快」「HTTP/3 用 UDP 所以更快」—— 这类说法对，但没说到点子上。

真正的主线只有一条：**队头阻塞（Head-of-Line Blocking）发生在哪一层。** 每一代 HTTP 都在解决上一代遗留的阻塞问题，而每次解决又暴露出新一层的阻塞。

理解了这条主线，三个版本的区别就不用背了。

---

## 一、三个版本各自解决了什么

先看全貌。注意：**版本号越大不代表"更好"**，而是各自在解决上一版的瓶颈。

	buttonText="点击加载版本演进图"
	height={480}
/>

| 版本 | 年份 | 核心突破 | 遗留问题 |
|---|---|---|---|
| **HTTP/1.0** | 1996 | 每请求一个连接 | 连接开销大 |
| **HTTP/1.1** | 1997 | 持久连接、管线化 | 应用层队头阻塞 |
| **HTTP/2** | 2015 | 二进制分帧、多路复用、HPACK | 传输层队头阻塞 |
| **HTTP/3** | 2022 | QUIC（基于 UDP）、QPACK | 部署与中间设备兼容性 |

> HTTP/0.9（1991）只有 GET、无头部，早就不用了，这里略过。

## 二、HTTP/1.1：应用层队头阻塞

### 2.1 持久连接（Keep-Alive）

HTTP/1.0 每次请求都要新建 TCP 连接 —— 三次握手 + 慢启动，代价很高。

HTTP/1.1 默认开启持久连接：**一个 TCP 连接可以依次处理多个请求**。

但这里有个关键限制：**同一连接上的请求必须一问一答**。前一个请求的响应没回来，后面的请求就不能发。

### 2.2 管线化：一次失败的尝试

HTTP/1.1 试图用**管线化（pipelining）**解决：不等响应，连续把多个请求发出去。

听起来能并行，但**响应仍必须按请求顺序返回** —— 因为客户端要靠顺序来匹配哪个响应对应哪个请求。

于是：

```
请求 A、B、C 依次发出
如果 A 的响应很慢（比如后端查库），B 和 C 即使早已处理完
也必须排在 A 后面等着 —— 这就是队头阻塞
```

**结果：主流浏览器全部默认关闭了管线化。** 取而代之的做法是**每个域名开 6 个左右的并发连接**，用"连接数"硬扛并发。

### 2.3 遗留的三个问题

1. **应用层队头阻塞**：一个连接上必须按序响应
2. **连接数上限**：6 个连接，第 7 个请求只能等
3. **头部重复传输**：每个请求都带一大坨几乎相同的头部（Cookie、User-Agent…），且**不压缩**

---

## 三、HTTP/2：解决应用层，但撞上传输层

HTTP/2 做了三件事，前两件直接针对 1.1 的痛点。

### 3.1 二进制分帧

HTTP/1.1 是**文本协议**：请求行、头部都是纯文本，解析要靠字符串匹配，容易出错（还记得请求走私吗）。

HTTP/2 把所有内容切成**二进制帧**：

| 帧类型 | 作用 |
|---|---|
| `HEADERS` | 请求/响应头 |
| `DATA` | 请求/响应体 |
| `SETTINGS` | 连接参数协商 |
| `WINDOW_UPDATE` | 流量控制 |
| `RST_STREAM` | 终止某个流 |

关键是**每个帧都带一个流 ID（Stream ID）**。

### 3.2 多路复用

有了流 ID，多个请求/响应就可以**交错着在同一条连接上传输**，接收端按流 ID 重新拼装。

<WhiteboardLoader
	elements={framingScene}
	label="HTTP/2 二进制分帧：三个请求被切成带流 ID 的帧，交错在同一条 TCP 连接上发送，接收端按流 ID 重新拼回各个请求"
	buttonText="点击加载分帧示意图"
	height={560}
/>

这就解决了**应用层**队头阻塞：慢的请求不再挡住快的请求，一个连接就能承载所有并发（不用再开 6 个）。

### 3.3 HPACK 头部压缩

HTTP/2 用 **HPACK** 压缩头部：

- 维护一张**静态表**（常见的头部名，如 `:method`、`content-type`）
- 加上一张**动态表**（连接期间出现过的头部）
- 重复的头部只发**索引号**，不再重复传字符串

对那种"每个请求都带 4KB Cookie"的场景，效果非常明显。

### 3.4 但 HTTP/2 仍会阻塞

多路复用只解决了**应用层**。往下看：所有流还是跑在**同一条 TCP 连接**上，而 **TCP 要求字节严格按序到达**。

```
流 1、2、3 的三个帧在同一连接上传输
如果流 2 的某个包丢了
→ TCP 不会把后面的字节交给上层（哪怕那是流 1、3 的数据）
→ 所有流一起等这个包重传
```

**这就是传输层队头阻塞。** 在网络好的环境下不明显，但在**移动网络**（丢包率 1%~5%）下，HTTP/2 甚至可能**比 HTTP/1.1 还慢** —— 因为 1.1 的 6 个连接里，丢包只影响其中一个。

> 另外两个值得知道的事：
> - **服务端推送（Server Push）已被淘汰**：Chrome 从 106 起移除了支持，HTTP/3 干脆没定义它。替代方案是 `103 Early Hints`。
> - **HTTP/2 的"快"更多来自头部压缩和连接复用**，而不是多路复用本身 —— 后者在丢包网络下反而会放大问题。

## 四、HTTP/3：把"有序"从传输层拿掉

HTTP/3 的核心是换了传输层：**不再用 TCP，改用基于 UDP 的 QUIC**。

### 4.1 队头阻塞的三个层次

这是全文的核心图 —— 同样三个请求，三种命运：

<WhiteboardLoader
	elements={holBlockingScene}
	label="队头阻塞的三个层次：HTTP/1.1 阻塞在应用层（同连接必须一问一答），HTTP/2 阻塞在传输层（TCP 要求字节按序到达，丢一个包所有流都等），HTTP/3 的 QUIC 流在传输层相互独立，丢包只影响该流"
	buttonText="点击加载队头阻塞对比图"
	height={540}
/>

QUIC 在**传输层**就把流做成了相互独立的：

- 每个流有自己的序号空间和重传逻辑
- 流 2 丢包，只重传流 2 的字节，**流 1、3 的数据照常交给上层**

这就消除了传输层队头阻塞 —— 也是 HTTP/3 存在的**根本理由**。

### 4.2 QPACK：为什么不能沿用 HPACK

HPACK 依赖"头部按序到达"来同步动态表。但 QUIC 的流是乱序的，HPACK 那套机制直接崩了。

所以 HTTP/3 用 **QPACK**：把动态表的更新放在**独立的单向流**上，并区分「需要等表更新的引用」和「不需要等的引用」，让乱序场景下也能安全压缩。

### 4.3 握手更快

<WhiteboardLoader
	elements={handshakeScene}
	label="建连耗时对比：HTTP/2 需要 TCP 三次握手 1 RTT 加 TLS 1.3 握手 1 RTT，共 2 RTT；HTTP/3 的 QUIC 把传输与加密握手合并为 1 RTT，复用会话时可 0 RTT，另有连接迁移能力"
	buttonText="点击加载握手耗时图"
	height={600}
/>

**HTTP/2（TCP + TLS 1.3）**：TCP 握手 1 RTT + TLS 握手 1 RTT = **2 RTT** 才能发第一个请求。

**HTTP/3（QUIC）**：把传输握手和加密握手**合并**，首次 **1 RTT**；再次连接同一服务器时可 **0 RTT**（直接带着数据发）。

RTT 越大差距越明显 —— 跨境访问时 2 RTT 可能就是几百毫秒。

### 4.4 连接迁移

QUIC 用**连接 ID** 标识连接，而不是靠「源 IP + 源端口」四元组。

好处：**手机从 Wi-Fi 切到 4G 时，IP 变了但连接还在**，不用重新握手、下载不会中断。这在 TCP 上做不到。

### 4.5 0-RTT 的安全代价

0-RTT 不是白拿的：**同一份 0-RTT 数据可能被攻击者截获后重放**（TLS 1.3 的固有问题）。

所以实践原则是：**只对幂等请求开启 0-RTT**。查询可以，下单、支付这类有副作用的操作不行。

## 五、横向对比

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | **QUIC（UDP）** |
| 报文格式 | 文本 | 二进制分帧 | 二进制分帧 |
| 并发方式 | 多连接（6/域名） | 单连接多路复用 | 单连接多路复用 |
| 队头阻塞 | **应用层** | **传输层** | **基本消除** |
| 头部压缩 | 无 | HPACK | QPACK |
| 建连耗时 | 1 RTT（+TLS） | 2 RTT（TCP+TLS 1.3） | 1 RTT / 0 RTT |
| 连接迁移 | 不支持 | 不支持 | **支持** |
| 加密 | 可选 | 事实强制（浏览器只支持 h2 over TLS） | **强制**（QUIC 内置 TLS 1.3） |
| 中间设备兼容 | 最好 | 好 | **较差**（UDP 常被限速/拦截） |

### 5.1 一个容易搞错的点：HTTP/2 不强制加密

标准上 HTTP/2 支持明文（`h2c`），但**浏览器只在 TLS 上实现 HTTP/2**。所以实际部署中 HTTP/2 基本等同于 HTTPS。

HTTP/3 则**强制加密** —— 因为 TLS 1.3 是 QUIC 协议的一部分，不是可选项。

### 5.2 另一个：版本是协商出来的

服务器不会"强制"用某个版本。客户端通过：

- **HTTP/2**：TLS 握手时用 ALPN 协商 `h2`
- **HTTP/3**：靠 `Alt-Svc` 响应头告诉客户端"我也支持 h3"

所以**首次访问可能走 HTTP/2，后续才切到 HTTP/3**。

## 六、实践：该用哪个

### 6.1 结论很简单：全都要开

现代部署的标准做法是**同时开启三个版本，让客户端自己协商**：

```
HTTP/1.1  ← 兜底，兼容一切老旧客户端
HTTP/2    ← 绝大多数客户端的默认
HTTP/3    ← 网络好的客户端自动升级
```

Nginx / Caddy / Envoy 都支持同时监听。

### 6.2 HTTP/3 的真实收益场景

| 场景 | 收益 |
|---|---|
| **移动网络 / 弱网** | 显著 —— 丢包不再拖累所有请求 |
| **跨境 / 高 RTT** | 明显 —— 省掉 1 RTT 握手 |
| **频繁切换网络**（移动端） | 明显 —— 连接迁移不断流 |
| 内网 / 低丢包有线网 | **很小** —— 没有丢包，队头阻塞不触发 |

**换句话说：HTTP/3 的收益与"网络有多差"正相关。** 在数据中心内部，它带来的提升可能还不如它引入的 CPU 开销（UDP 处理、用户态协议栈）。

### 6.3 HTTP/3 的部署代价

- **UDP 常被中间设备限制**：部分企业防火墙、老的路由器会限速甚至丢弃 UDP 443，导致降级
- **CPU 开销更高**：QUIC 多在用户态实现，比内核 TCP 栈更耗 CPU
- **排障工具不成熟**：抓包分析 UDP 比 TCP 麻烦得多（不过 Wireshark 已支持 QUIC 解密）

## 七、总结

回到那条主线 —— **每一代都在解决上一代遗留的阻塞**：

| 版本 | 解决了什么 | 又暴露了什么 |
|---|---|---|
| HTTP/1.1 | 连接复用（持久连接） | 应用层队头阻塞（必须按序响应） |
| HTTP/2 | 应用层队头阻塞（多路复用） | **传输层**队头阻塞（TCP 要求按序） |
| HTTP/3 | 传输层队头阻塞（QUIC 独立流） | 部署兼容性、CPU 开销 |

三句话记住区别：

1. **HTTP/1.1 的瓶颈是"一个连接只能按序来"** → 所以开 6 个连接硬扛
2. **HTTP/2 的瓶颈是"TCP 要求字节按序"** → 丢一个包，所有流一起等
3. **HTTP/3 把"有序"这个约束从传输层拿掉** → 流之间彻底独立，顺带握手更快、还能连接迁移

最后提醒一句：**别把 HTTP/3 当成无脑升级**。它的收益在弱网和高 RTT 下最明显；如果你的用户都在低延迟有线网络里，收益有限，而部署复杂度是实打实的。
